#+TITLE: Práctica 04: Cortafuegos con iptables en un router Docker

* Prompt :noexport:


Inventa una práctica para ASIR grado superior módulo Seguridad y alta disponibilidad RA4.

Usa contenedores docker para crear un router, una red interna y la red real del host, y contenedores en la red interna.

En la red interna habrá servicios (por ejemplo http, mysql), y en el router habrá reglas de iptables para controlar quién puede acceder


* Objetivo de la práctica

Al finalizar la práctica, el alumno será capaz de:

- Desplegar con /Docker/ una topología formada por una red externa, un router /Linux/ y una red interna aislada.
- Comprobar que cada contenedor tiene su propia pila de red y sus propias tablas de =iptables=, independientes de las del host.
- Publicar los servicios de la red interna hacia la red externa mediante =DNAT=.
- Justificar y aplicar el =SNAT= necesario para que el tráfico publicado funcione en una red =internal= de /Docker/.
- Filtrar el tráfico con =iptables= usando políticas por defecto restrictivas y reglas de excepción.
- Restringir el acceso a un servicio (/MySQL/) a un único cliente autorizado.
- Registrar en el log del kernel los intentos de acceso bloqueados y revisarlos.
- Diagnosticar problemas de conectividad provocados por el cortafuegos.
- Documentar las reglas y automatizar su aplicación.

Está disponible la [[https://alvarogonzalezsotillo.github.io/apuntes-clase/seguridad-alta-disponibilidad/apuntes/4/sad-04-practica-cortafuegos-docker.pdf][última versión de esta práctica en este enlace]].

* Descripción del escenario

Se parte del fichero [[file:docker-compose.yml][docker-compose.yml]] incluido en esta carpeta. En él ya están definidos:

- La red =wan= (=172.30.0.0/24=), una red puente accesible desde el host, que representa la red real del host o la red externa del aula.
- La red =lan= (=192.168.50.0/24=), declarada como =internal: true=, de modo que /Docker/ la aísla del exterior.
- El contenedor =router= (=ubuntu:24.04=), con dos interfaces:
  - =eth0= en =wan=, con IP =172.30.0.2=.
  - =eth1= en =lan=, con IP =192.168.50.2=.
- El reenvío IP activado en el router.

El host tiene la IP =172.30.0.1= en la red =wan= y actúa como cliente externo. Los servicios que hay que añadir en la red interna son:

| Servicio | Contenedor | IP            | Puerto   |
|----------+------------+---------------+----------|
| HTTP     | =http=     | 192.168.50.10 | 80/tcp   |
| MySQL    | =mysql=    | 192.168.50.20 | 3306/tcp |

Además se añadirá un cliente externo de administración:

| Cliente        | Contenedor      | IP           |
|----------------+-----------------+--------------|
| Administración | =cliente-admin= | 172.30.0.100 |

El objetivo es que:

- Cualquier cliente de la red =wan= (por ejemplo, el propio host) pueda acceder al servidor HTTP mediante =http://172.30.0.2:8080=.
- Solo =cliente-admin= (=172.30.0.100=) pueda acceder al servidor MySQL en =172.30.0.2:3306=.
- Los intentos de acceso no autorizados a MySQL queden registrados en el log.
- Ningún otro tráfico atraviese el router hacia la red interna.

** Completar el escenario

Amplía el fichero =docker-compose.yml= para añadir los contenedores =http=, =mysql= y =cliente-admin=:

- =http=:
  - Imagen =nginx:alpine=.
  - IP fija =192.168.50.10= en la red =lan=.
  - Una página =index.html= personalizada, montada en =/usr/share/nginx/html/index.html=.
- =mysql=:
  - Imagen =mariadb:11=.
  - IP fija =192.168.50.20= en la red =lan=.
  - Variables =MARIADB_ROOT_PASSWORD=, =MARIADB_DATABASE=, =MARIADB_USER= y =MARIADB_PASSWORD=.
- =cliente-admin=:
  - Imagen =mariadb:11=, que ya incluye el cliente =mariadb=.
  - IP fija =172.30.0.100= en la red =wan=.
  - =entrypoint: ["sleep", "infinity"]=, para que no arranque ningún servidor y podamos usarlo como cliente.

Levanta el escenario y comprueba las redes y las IPs asignadas:

#+begin_src bash
docker compose up -d
docker compose ps
docker network ls
docker network inspect 4_wan
docker network inspect 4_lan
#+end_src

El prefijo de las redes (=4=) depende del nombre del directorio del proyecto.

Comprueba el punto de partida antes de filtrar nada:

#+begin_src bash
# El router es accesible desde el host
ping -c 2 172.30.0.2

# Todavía no hay nada publicado en el puerto 8080 del router
curl -m 3 http://172.30.0.2:8080/
#+end_src

La segunda orden falla con /connection refused/: el router no está escuchando en el 8080, pero todavía /contesta/ con un rechazo. Más adelante, cuando el cortafuegos empiece a descartar paquetes, el fallo será por /timeout/: conviene notar la diferencia.

Comprueba también que la red =lan= está realmente aislada para los clientes externos: =cliente-admin= no puede llegar a los servidores aunque conozca sus IPs.

#+begin_src bash
docker exec cliente-admin mariadb --connect-timeout=3 \
  -h 192.168.50.10 -P 3306 -u root -pnoexiste -e "SELECT 1;"
#+end_src

El cliente no consigue conectar: /Docker/ descarta en el host el tráfico que, procedente de otras redes, se dirige hacia un puente =internal=. Solo queda el camino del router, que es lo que vamos a controlar.

** Preparar el router

Entra en el router e instala las herramientas que necesitarás para el cortafuegos y para diagnosticar:

#+begin_src bash
docker exec -it router bash
apt-get update
apt-get install -y iptables iproute2 iputils-ping curl tcpdump conntrack
#+end_src

Comprueba las interfaces, las rutas y el reenvío:

#+begin_src bash
ip address
ip route
sysctl net.ipv4.ip_forward
#+end_src

Observa las tablas de =iptables= del router:

#+begin_src bash
iptables -L -n -v
iptables -t nat -L -n -v
#+end_src

Están prácticamente vacías. Cada contenedor tiene su /propia/ pila de red y sus propias tablas, independientes de las del host. Compáralas con las que /Docker/ mantiene en el host (fuera del contenedor, con =sudo=):

#+begin_src bash
sudo iptables -L -n -v
sudo iptables-save | grep -i docker
#+end_src

En el host verás cadenas como =DOCKER=, =DOCKER-FORWARD=, =DOCKER-INTERNAL= y =DOCKER-USER= (en versiones anteriores, =DOCKER-ISOLATION-STAGE-1= y =DOCKER-ISOLATION-STAGE-2=). Son las que /Docker/ usa para gestionar sus puentes y aislar las redes internas, y conviene conocerlas porque explican parte del comportamiento del escenario.

** Políticas por defecto y tráfico básico

Aplica políticas por defecto restrictivas y permite únicamente el tráfico imprescindible para el diagnóstico:

#+begin_src bash
# Politicas por defecto
iptables -P INPUT DROP
iptables -P FORWARD DROP
iptables -P OUTPUT ACCEPT

# Loopback y conexiones ya establecidas
iptables -A INPUT -i lo -j ACCEPT
iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
iptables -A FORWARD -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT

# Diagnostico: permitir ping al router desde la red externa
iptables -A INPUT -i eth0 -p icmp --icmp-type echo-request -j ACCEPT
#+end_src

Comprueba que el router sigue respondiendo a =ping= desde el host y que ahora el puerto 8080 ni siquiera rechaza la conexión:

#+begin_src bash
ping -c 2 172.30.0.2
curl -m 3 http://172.30.0.2:8080/
#+end_src

Con =INPUT= y =FORWARD= en =DROP=, ningún tráfico atraviesa todavía el router hacia la red interna.

** Publicar HTTP con DNAT

Publica el servidor HTTP de la red interna en el puerto =8080= del router. Una primera aproximación razonable sería hacer solo =DNAT= y permitir el reenvío:

#+begin_src bash
# Redirigir el trafico que llega al router por el puerto 8080
iptables -t nat -A PREROUTING -i eth0 -d 172.30.0.2 \
  -p tcp --dport 8080 -j DNAT --to-destination 192.168.50.10:80

# Permitir el trafico reenviado hacia el servidor HTTP
iptables -A FORWARD -i eth0 -o eth1 -p tcp \
  -d 192.168.50.10 --dport 80 \
  -m conntrack --ctstate NEW,ESTABLISHED,RELATED -j ACCEPT
#+end_src

Comprueba desde el host:

#+begin_src bash
curl -m 3 http://172.30.0.2:8080/
#+end_src

*No funciona.* Diagnostica el problema con =tcpdump= en el router mientras repites el =curl= desde el host:

#+begin_src bash
tcpdump -ni eth1 tcp port 80
#+end_src

Ves los =SYN= saliendo por =eth1= hacia =192.168.50.10=, pero nunca vuelve ninguna respuesta: el paquete sale del router y no llega al servidor. La explicación está en el host: mira las reglas que /Docker/ instala para la red interna.

#+begin_src bash
sudo iptables-save | grep -A5 DOCKER-INTERNAL
# o, en versiones anteriores de Docker:
sudo iptables-save | grep -A5 DOCKER-ISOLATION-STAGE-1
#+end_src

Entre las reglas aparecen dos como estas (donde =br-XXXX= es el puente de la red =lan=):

#+begin_example
-A DOCKER-INTERNAL ! -s 192.168.50.0/24 -o br-XXXX -j DROP
-A DOCKER-INTERNAL ! -d 192.168.50.0/24 -i br-XXXX -j DROP
#+end_example

/Docker/ descarta en el host cualquier paquete que circule por el puente de una red =internal= con una IP de origen o de destino ajena a la subred. El paquete que hemos reenviado llega al puente con su origen original (=172.30.0.1=), así que el host lo descarta antes de que alcance al contenedor =http=.

La solución es que el router /enmascare/ ese tráfico con su propia IP de la red interna:

#+begin_src bash
# SNAT del trafico que el router reenvia hacia la lan
iptables -t nat -A POSTROUTING -o eth1 -d 192.168.50.0/24 \
  -j SNAT --to-source 192.168.50.2
#+end_src

Ahora el paquete entra en el puente con origen =192.168.50.2= (una IP de la subred), y la respuesta del servidor vuelve directamente al router, que restaura las IPs originales gracias a =conntrack=. Compruébalo:

#+begin_src bash
curl -v http://172.30.0.2:8080/
#+end_src

Debe aparecer la página personalizada. Comprueba también que el puerto 80 del router /no/ está publicado:

#+begin_src bash
curl -m 3 http://172.30.0.2:80/
#+end_src

Como efecto secundario del =SNAT=, el servidor HTTP ve las conexiones como si vinieran del router. Observa el log de accesos:

#+begin_src bash
docker logs http
#+end_src

Y revisa en el router las entradas de =conntrack= de la conexión que acabas de hacer:

#+begin_src bash
conntrack -L | grep 192.168.50
#+end_src

*Nota:* en un router físico, con los servidores usando al router como puerta de enlace, este =SNAT= no sería necesario. En este escenario hace falta precisamente por el aislamiento que /Docker/ aplica a las redes =internal=. Es el precio de que el host controle el acceso a la red interna y de que los servidores no necesiten ruta por defecto hacia el router: las respuestas vuelven a él por estar en la misma subred.

** Publicar MySQL con acceso restringido

Publica MySQL en el puerto =3306= del router, pero permite el acceso únicamente al cliente de administración:

#+begin_src bash
# Redirigir el trafico del puerto 3306 al servidor MySQL
iptables -t nat -A PREROUTING -i eth0 -d 172.30.0.2 \
  -p tcp --dport 3306 -j DNAT --to-destination 192.168.50.20:3306

# Permitir solo al cliente 172.30.0.100
iptables -A FORWARD -i eth0 -o eth1 -s 172.30.0.100 \
  -p tcp -d 192.168.50.20 --dport 3306 \
  -m conntrack --ctstate NEW,ESTABLISHED,RELATED -j ACCEPT

# Registrar y bloquear el resto de intentos
iptables -A FORWARD -i eth0 -o eth1 -p tcp \
  -d 192.168.50.20 --dport 3306 \
  -j LOG --log-prefix "MYSQL-DENEGADO: " --log-level 4
iptables -A FORWARD -i eth0 -o eth1 -p tcp \
  -d 192.168.50.20 --dport 3306 -j DROP
#+end_src

Fíjate en el orden: la regla que acepta a =cliente-admin= debe estar /antes/ que las de =LOG= y =DROP=. El destino =LOG= no bloquea nada por sí mismo: solo registra el paquete y deja que siga evaluando reglas.

La regla de =SNAT= del paso anterior también se aplica a estas conexiones, así que el procedimiento es el mismo que con HTTP.

Comprueba el acceso desde =cliente-admin=:

#+begin_src bash
docker exec cliente-admin mariadb --connect-timeout=5 \
  -h 172.30.0.2 -P 3306 -u alumno -palumno1234 \
  -e "SELECT VERSION();"
#+end_src

Debe responder con la versión de /MariaDB/. Comprueba desde el host que el acceso está bloqueado:

#+begin_src bash
timeout 5 bash -c 'cat < /dev/null > /dev/tcp/172.30.0.2/3306'
echo $?
#+end_src

El comando debe terminar con un código distinto de =0= y agotar el /timeout/ (un =DROP= no rechaza la conexión: la silencia). Revisa los intentos bloqueados en el log del kernel del host (el kernel es compartido entre el host y los contenedores, así que los mensajes de =iptables -j LOG= del router aparecen ahí):

#+begin_src bash
sudo dmesg | grep MYSQL-DENEGADO
# o, si tu sistema usa journald:
sudo journalctl -k | grep MYSQL-DENEGADO
#+end_src

** Guardar y automatizar las reglas

Las reglas de =iptables= se pierden si el contenedor se reinicia. Reúnelas todas en un script =router/firewall.sh=, móntalo en el router con un volumen y ejecútalo tras levantar el escenario:

#+begin_src yaml
  router:
    volumes:
      - ./router/firewall.sh:/firewall.sh:ro
#+end_src

#+begin_src bash
docker exec router bash /firewall.sh
#+end_src

Como alternativa puedes volcar y restaurar las reglas con =iptables-save= e =iptables-restore= (fíjate en la opción =-i= para pasar el fichero por la entrada estándar):

#+begin_src bash
docker exec router iptables-save > router/rules.v4
docker exec -i router iptables-restore < router/rules.v4
#+end_src

** docker-compose.yml completo

#+begin_src yaml
services:
  router:
    image: ubuntu:24.04
    container_name: router
    cap_add:
      - NET_ADMIN
    sysctls:
      net.ipv4.ip_forward: "1"
    networks:
      wan:
        interface_name: eth0
        ipv4_address: 172.30.0.2
      lan:
        interface_name: eth1
        ipv4_address: 192.168.50.2
    volumes:
      - ./router/firewall.sh:/firewall.sh:ro
    command: >
      bash -c "apt-get update &&
               apt-get install -y iptables iproute2 iputils-ping curl tcpdump conntrack &&
               sleep infinity"

  http:
    image: nginx:alpine
    container_name: http
    volumes:
      - ./http/index.html:/usr/share/nginx/html/index.html:ro
    networks:
      lan:
        ipv4_address: 192.168.50.10

  mysql:
    image: mariadb:11
    container_name: mysql
    environment:
      MARIADB_ROOT_PASSWORD: root1234
      MARIADB_DATABASE: practica
      MARIADB_USER: alumno
      MARIADB_PASSWORD: alumno1234
    networks:
      lan:
        ipv4_address: 192.168.50.20

  cliente-admin:
    image: mariadb:11
    container_name: cliente-admin
    entrypoint: ["sleep", "infinity"]
    networks:
      wan:
        ipv4_address: 172.30.0.100

networks:
  wan:
    driver: bridge
    ipam:
      config:
        - subnet: 172.30.0.0/24

  lan:
    driver: bridge
    internal: true
    ipam:
      config:
        - subnet: 192.168.50.0/24
#+end_src

** router/firewall.sh

#+begin_src bash
#!/bin/bash
# Cortafuegos de la practica 04.
# Ejecutar como root dentro del contenedor router:
#   docker exec router bash /firewall.sh

set -e

WAN_IF=eth0
LAN_IF=eth1
WAN_IP=172.30.0.2
LAN_IP=192.168.50.2
LAN_NET=192.168.50.0/24
HTTP_IP=192.168.50.10
MYSQL_IP=192.168.50.20
ADMIN_IP=172.30.0.100

# Limpiar reglas anteriores
iptables -F
iptables -t nat -F

# Politicas por defecto
iptables -P INPUT DROP
iptables -P FORWARD DROP
iptables -P OUTPUT ACCEPT

# Loopback y conexiones establecidas
iptables -A INPUT -i lo -j ACCEPT
iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
iptables -A FORWARD -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT

# Diagnostico: ping al router desde la WAN
iptables -A INPUT -i "$WAN_IF" -p icmp --icmp-type echo-request -j ACCEPT

# Publicacion de HTTP: 172.30.0.2:8080 -> 192.168.50.10:80
iptables -t nat -A PREROUTING -i "$WAN_IF" -d "$WAN_IP" \
  -p tcp --dport 8080 -j DNAT --to-destination "$HTTP_IP":80
iptables -A FORWARD -i "$WAN_IF" -o "$LAN_IF" -p tcp \
  -d "$HTTP_IP" --dport 80 \
  -m conntrack --ctstate NEW,ESTABLISHED,RELATED -j ACCEPT

# Publicacion de MySQL: 172.30.0.2:3306 -> 192.168.50.20:3306
iptables -t nat -A PREROUTING -i "$WAN_IF" -d "$WAN_IP" \
  -p tcp --dport 3306 -j DNAT --to-destination "$MYSQL_IP":3306

# Solo el cliente de administracion puede acceder a MySQL
iptables -A FORWARD -i "$WAN_IF" -o "$LAN_IF" -s "$ADMIN_IP" \
  -p tcp -d "$MYSQL_IP" --dport 3306 \
  -m conntrack --ctstate NEW,ESTABLISHED,RELATED -j ACCEPT

# Registrar y bloquear el resto de intentos a MySQL
iptables -A FORWARD -i "$WAN_IF" -o "$LAN_IF" -p tcp \
  -d "$MYSQL_IP" --dport 3306 \
  -j LOG --log-prefix "MYSQL-DENEGADO: " --log-level 4
iptables -A FORWARD -i "$WAN_IF" -o "$LAN_IF" -p tcp \
  -d "$MYSQL_IP" --dport 3306 -j DROP

# SNAT del trafico reenviado hacia la LAN. Necesario por el
# aislamiento que Docker aplica a las redes internal (ver la
# practica): sin el, el host descarta los paquetes DNATeados
# por llegar al puente de la lan con un origen ajeno a la subred.
iptables -t nat -A POSTROUTING -o "$LAN_IF" -d "$LAN_NET" \
  -j SNAT --to-source "$LAN_IP"

echo "Reglas aplicadas correctamente."
#+end_src

** Nota sobre la salida a Internet de la red interna

Una regla =MASQUERADE= clásica en el router (por ejemplo =iptables -t nat -A POSTROUTING -o eth0 -s 192.168.50.0/24 -j MASQUERADE=) *no* consigue que los contenedores de la =lan= salgan a Internet. El motivo es el mismo aislamiento que obliga al =SNAT= del paso /Publicar HTTP con DNAT/: /Docker/ instala en el host reglas que descartan, en el puente de la red interna, cualquier paquete con origen o destino fuera de la subred (=DOCKER-INTERNAL=, o =DOCKER-ISOLATION-STAGE-1/2= en versiones anteriores). El paquete de un contenedor de la =lan= dirigido a Internet se descarta en el host antes de llegar al router.

Si algún día se necesitara salida a Internet desde la =lan=, habría que permitirla expresamente en el host (por ejemplo, una regla =ACCEPT= para ese puente en la cadena =DOCKER-USER=, que es la primera que se evalúa en =FORWARD=), configurar la ruta por defecto de los contenedores hacia el router y, efectivamente, usar =MASQUERADE= o =SNAT=. Eso rompería el aislamiento que precisamente buscamos con =internal: true=, así que en esta práctica la red interna no tiene salida directa: es una decisión de diseño, no una limitación del router.

** Respuestas orientativas al diagnóstico

1. Con =tcpdump -ni eth1= se ve si los paquetes salen hacia el servidor y si vuelve la respuesta; =iptables -t nat -L -n -v= debe mostrar el =DNAT= del 8080 y la regla de =SNAT=, y =iptables -L FORWARD -n -v= el =ACCEPT= hacia el servidor. Si todo está en el router, hay que mirar las reglas de aislamiento que /Docker/ instala en el host.
2. Falta la regla que acepta =NEW= desde =172.30.0.100= hacia el =MySQL= publicado, o está colocada después del =DROP=. El =ping= al router no se ve afectado porque va a =INPUT=, no a =FORWARD=.
3. Porque el router hace =SNAT= a =192.168.50.2= para que el tráfico DNATEado atraviese el puente interno. Para el servidor, todos los clientes externos son el router: no puede distinguirlos por IP (inconveniente para logs o ACLs), pero la respuesta siempre vuelve por el router (ventaja: los servidores no necesitan puerta de enlace hacia él).
4. /Docker/ descarta en el host, dentro de =FORWARD= (cadena =DOCKER-INTERNAL= o =DOCKER-ISOLATION-STAGE-1=), cualquier paquete del puente de la =lan= con origen o destino fuera de =192.168.50.0/24=, por lo que el tráfico muere antes de salir de la red interna, con o sin =MASQUERADE=.
5. Guardando las reglas (=firewall.sh=, =iptables-save=) y aplicándolas tras cada arranque: con un volumen montado y =docker exec=, o como parte del =command= del servicio.
6. El host sí puede alcanzar directamente =192.168.50.10=, mientras que =cliente-admin= no puede. Las reglas de aislamiento viven en la cadena =FORWARD= del host, que solo atraviesa el tráfico reenviado o puenteado; el tráfico generado por el propio host sale por =OUTPUT= y no pasa por =FORWARD=. El host es un caso especial por ser la máquina donde reside /Docker/: el control de acceso real lo ejerce el router sobre los clientes externos.
